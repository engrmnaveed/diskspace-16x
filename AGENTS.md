# Working on Space 16X

- `Sources/SpaceApp` and `Sources/SpaceCore` implement the macOS app in Swift. `cli/` is the Rust CLI for macOS and Linux. Cargo uses the pinned toolchain in `cli/rust-toolchain.toml`.
- Keep the scanners read-only and metadata-only. The only change to the user's files is a user-confirmed Move to Trash (`cli/src/trash.rs` in the CLI, `FileManager.trashItem` in the app). It moves items to the Trash on their own disk and never copies them or deletes them permanently. Besides that, Space 16X writes only an export or report file the user names (`scan --export FILE`, Pro's `scan --html FILE`, the app's Export Scan) and, in Pro, a scan the user saves to the history (`space16x history save` into `$XDG_STATE_HOME/space16x/history`, the app's Save to History into `~/Library/Application Support/Space 16X/History`). Imported scans stay read-only. Read file contents only on an explicit user action, never during a scan: Pro's `space16x duplicates` and the app's Find Duplicates are the only readers. Maintain allocated-byte accounting, hard-link deduplication, symlink and device boundaries, and explicit partial results. Use synthetic fixtures to exercise changes on both scanners when shared behavior is affected.
- Preserve the versioned CLI report and exit-status contract in [docs/cli.md](docs/cli.md), with Pro's commands in [docs/cli-pro.md](docs/cli-pro.md), which only the Pro archive ships. Synchronize CLI and bundle release versions through `cli/Cargo.toml` and `scripts/release-version`.
- For Rust changes, run `(cd cli && cargo fmt --all --check && cargo clippy --locked --all-targets -- -D warnings && cargo test --locked)`. Build the CLI and run `scripts/check-cli.py` and `scripts/check-tui.py` with its executable. Run `python3 scripts/check-install.py` when editing the installer.
- For Swift changes, run `swift test` and `scripts/package-macos.sh` on macOS. Use the [manual checklist](docs/manual-qa.md) for UI behavior.
- Run permission checks as a standard user. Keep signing, credentials, and publication in the [release workflow](docs/release.md).
- A noticeable, major UI/UX change or major user-facing feature must refresh the [promotional video](docs/promo.md) in the same change. Update the storyboard or capture under `scripts/promo/` (or `scripts/build-promo.py`) to demonstrate the feature. On macOS, run the promo generator, review the MP4, and refresh `Branding/Space16X-Demo.gif`. On other platforms, use the macOS Promo video workflow artifact to review and refresh the GIF. Include “New promo ready to publish” with the MP4 or Actions artifact link in the handoff once rendering succeeds. The workflow renders on qualifying changes and notifies the repository owner when a new Short is ready on `main`.
- Space 16X has two free editions, Basic and Pro ([roadmap §3](docs/roadmap.md#3-the-edition-rule)). Put a feature in Pro if it adds per-item memory, a dependency, state on disk, background work, file-content reads, or significant UI. Keep Basic light enough for remote servers. Once the `pro` feature exists, build and test both editions for every change.
- The roadmap and its progress live in [docs/roadmap.md](docs/roadmap.md). Read its Progress, Working agreement and How to resume sections before roadmap work, and keep Progress current in the same PR as each item.
